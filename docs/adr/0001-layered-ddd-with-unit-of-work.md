# ADR 0001. Слоистый DDD с репозиториями и Unit of Work

Статус: принято, 2026-07-26

## Контекст

Система сочетает три источника сложности: доменную логику ревью, работу с БД
(индекс кода, находки, метрики) и медленные внешние вызовы (LLM, git, линтеры).
Без явных границ такие проекты быстро вырождаются в набор функций, где транзакции
открываются в случайных местах, а тесты требуют поднятой инфраструктуры.

## Решение

Слои с зависимостями, направленными внутрь:

```
apps → application → core (домен) ← инфраструктура
```

- `core` объявляет порты (`Protocol`) и не импортирует ничего, кроме stdlib и pydantic.
- `application` содержит use cases и владеет границей транзакции.
- Инфраструктура (`storage`, `llm`, `indexing`, `vcs`) реализует порты.
- Доступ к данным — только через репозитории агрегатов.
- Транзакция — явный `UnitOfWork`, открываемый use case'ом. Репозиторий не коммитит.
- ORM-модели отделены от доменных сущностей явным отображением.
- Доменные события собираются UoW и публикуются после успешного коммита.

Правило зависимостей проверяется `import-linter` в CI.

## Последствия

Положительные:

- Логика ревью тестируется на фейковом UoW, без контейнеров и без сети.
- Атомарность там, где она нужна: снапшот индекса готов целиком либо не существует.
- Замена провайдера LLM или векторного поиска не трогает домен.

Отрицательные:

- Больше кода: отображение ORM ↔ домен, порты, явная сборка зависимостей.
- Выше порог входа в кодовую базу.

Компромисс принят сознательно: дописать слои задним числом невозможно.

## Границы применения

DDD используется как дисциплина слоёв и транзакций, а не как ритуал. Отклонены:
event sourcing, CQRS с раздельными моделями, фабрики и спецификации без нужды,
доменные сервисы на каждую операцию.

## Ключевое эксплуатационное правило

Долгие операции (LLM, git, линтеры) не выполняются внутри открытой транзакции:
чтение в транзакции → работа вне транзакции → короткая транзакция на запись.
Иначе пул соединений исчерпывается на первых параллельных прогонах.
